# AcceptBox

[English](README.md) · **Русский**

**Инструмент независимой приёмки багфиксов по цепочке Git-коммитов (`base → repro → head`).**

Когда разработчик или ИИ-агент приносит багфикс, зелёные тесты на последнем коммите ещё не доказывают, что баг действительно воспроизвели и починили: тест мог быть зелёным и до правки, либо коммит с фиксом мог незаметно ослабить или удалить тест.

AcceptBox проверяет цепочку из трёх коммитов в изолированных временных Git worktree (не переключая ваше рабочее дерево) и атомарно записывает машиночитаемый вердикт (`accept.json`):

1. **`base`** — исходный коммит (например, в `main`), в котором баг присутствует.
2. **`repro`** — коммит, который *только* добавляет падающий репро-тест (доказывая, что баг действительно воспроизводится).
3. **`head`** — коммит с исправлением, на котором тесты становятся зелёными, *без изменения, переименования или удаления* репро-теста и защищённых файлов.

Runtime использует только стандартную библиотеку Python (`>=3.11`) и не имеет сторонних зависимостей.

## Два режима приёмки

- **Режим `command` (по умолчанию, автономный)** — работает с любым тестовым фреймворком (`unittest`, `pytest`, `vitest`, `go test`, `cargo test`, `flutter test`, Gradle и т. д.) без дополнительных инструментов. Проверяет, что `repro` меняет только пути внутри `--tests` и падает с кодом `1` (`red`), а `head` не трогает эти тестовые файлы и проходит с кодом `0` (`green`).
- **Режим `witnessbox` (опциональный)** — интеграция с [WitnessBox](https://github.com/kaufd/witnessbox) (`>=0.10.0`) для тестирования на основе свидетельств (EBT). Проверяет утверждённое человеком дерево `ebt/` по зафиксированному SHA-256 (`acceptbox pin`), убеждается, что `base` и `repro` падают по целевому инварианту (`FALSE_PROOF` / `CONFIRMED_VIOLATION`), а `head` проходит.

## Быстрый старт

### 1. Установка

```sh
uv tool install acceptbox
acceptbox --installation
```

*(Опционально, только для `--mode witnessbox`: `uv tool install 'witnessbox>=0.10.0'`.)*

### 2. Один раз настройте проект (`.acceptbox.toml` в `main`)

Закоммитьте `.acceptbox.toml` в базовую ветку, чтобы не повторять флаги при каждом запуске:

```toml
format = 1
mode = "command"
protect = ["pyproject.toml"]

[command]
tests = ["tests/"]
argv = ["python3", "-m", "unittest", "discover", "-s", "tests"]
```

AcceptBox читает `.acceptbox.toml` строго из объектов Git коммита `base` и автоматически защищает его от изменений в `base..repro` и `base..head`. Не хотите коммитить служебные файлы в целевой репозиторий? Держите конфиг снаружи (см. [example/acceptbox.toml](example/acceptbox.toml)) и передавайте `--config /path/to/acceptbox.toml`.

### 3. Сделайте багфикс в виде `base → repro → head`

```sh
# Стартуя от коммита в main (base):
# 1) Добавьте падающий репро-тест в tests/ и закоммитьте:
git commit -m "test: reproduce bug #123"
REPRO=$(git rev-parse HEAD)

# 2) Исправьте баг в коде приложения (не трогая репро-тест) и закоммитьте:
git commit -m "fix: handle empty input (#123)"
```

### 4. Запустите приёмку

```sh
acceptbox accept --base-ref main
```

Когда в `main` есть `.acceptbox.toml`, AcceptBox сам вычислит `base` (`merge-base main HEAD`), `repro` (коммит с trailer `AcceptBox-Role: repro` или первый коммит в `base..HEAD`) и `head` (`HEAD`). Для ветки рефакторинга (`base` зелёный → `head` зелёный, тесты защищены) выполните `acceptbox accept --policy refactor --base-ref main`.

AcceptBox напечатает вердикт и путь к `accept.json` (создаётся атомарно в новом пустом каталоге в `TMPDIR` или в `--out <пустой-каталог>`):

- Код `0` — **`ACCEPTED`** (все условия приёмки выполнены).
- Код `1` — **`REJECTED`** (нарушено правило приёмки: например, `base-not-on-ref`, `repro-outside-tests`, `repro-tests-modified`, `protected-paths-changed`, `repro-green`, `head-not-green`).
- Код `2` — **`ERROR`** (ошибка CLI/конфига/окружения/git или сбой запуска тестов с кодом `>= 2`).

Чтобы получить читаемую сводку в Markdown или автономный HTML5-отчёт из `accept.json` (или `calibrate.json`):

```sh
acceptbox render /path/to/accept.json --format md
acceptbox render /path/to/accept.json --format html --out report.html
```

> **Подключаете с помощью ИИ-агента?** Дайте ему [инструкцию для агента](docs/agent.ru.md) — он сам подготовит `.acceptbox.toml`, обёртку тестов и правила для агентов проекта, остановившись в нужных точках для утверждения человеком.

## Когда использовать AcceptBox (и когда не стоит)

- **Багфиксы** (режим `command` или `witnessbox`): основное назначение цепочки `base → repro → head`.
- **Утверждённые человеком инварианты** (режим `witnessbox`): подходит и для багфиксов, и для фич, если человек утвердил `ebt/spec.toml` до реализации.
- **Новые фичи без утверждённой спецификации** (`--policy feature`): проверяет, что `head` зелёный, существующие тесты не тронуты, а новые тестовые файлы добавлены, — но **не** проверяет соответствие фичи замыслу. Чтобы проверить замысел, используйте утверждённую человеком спецификацию (режим `witnessbox`) и/или проверку сценариев с одобрением человеком (см. [проверку фичи для оркестратора или агента-проверяющего](docs/agent.ru.md#7-проверка-фичи-для-оркестратора-или-агента-проверяющего)).
- **Рефакторинги** (`--policy refactor`, `base` зелёный → `head` зелёный без `--repro`): ортогонально `--mode`; проверяет, что и `base`, и `head` проходят, автоматически защищая `.acceptbox.toml` и `[command].tests` (или `ebt/` и `tool/ebt_check` в режиме `witnessbox`).

## Гарантии и границы

AcceptBox проверяет структуру коммитов, неизменность файлов и запускает тесты в чистых worktree, но **не является песочницей ОС**: тестовая команда выполняется от имени того же пользователя ОС.

- **Граница доверия `.acceptbox.toml`:** конфиг читается строго из `base` и автоматически защищён, поэтому ему можно доверять настолько, насколько можно доверять `--base`. Передавайте `--base-ref main` (только CLI): AcceptBox до чтения конфига проверит, что `--base` — предок `main` из `origin`. В CI добавляйте `--strict-refs`, чтобы fail-closed запретить слабый запасной путь `"local"` (`ref-source-local`). Без `--base-ref` значение `--base` должна задавать принимающая сторона (человек, CI или внешний оркестратор), а не проверяемый агент.
- **Граница доверия локального `.git/config`:** для локального `--repo` / `--ebt-repo` AcceptBox берёт `--base-ref` и `--ebt-ref` из remote `origin` (а если `origin` нет — из локальной ветки с пометкой `ref_source_kind: "local"`, если не задан `--strict-refs`). Агент с правом записи в `.git/config` может перенаправить или удалить `origin`. Всегда проверяйте `ref_source` и `ref_source_kind` в `accept.json`; для полной гарантии запускайте приёмку вне досягаемости агента (CI) или передавайте `--repo` / `--ebt-repo` как URL репозитория.
- **Смысловое качество теста в режиме `command`:** режим `command` доказывает, что `repro` затронул только `--tests`, упал с кодом `1` и не был изменён в `head`, который затем прошёл с кодом `0`. Проверку того, что тест действительно проверяет нужный баг, выполняет человек на ревью — либо используйте режим `witnessbox` для независимой проверки инвариантов.
- **Среда в чистом worktree:** каждый коммит прогоняется в свежем detached-worktree с очищенным окружением. Если проекту нужна установка зависимостей или сборка, оформите скрипт-обёртку, который возвращает код `>= 2` при сбое подготовки и `1` *только* при провале тестов (см. [Настройка проекта и шаблоны](docs/setup.ru.md)).
